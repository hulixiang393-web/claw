# claw 多源爬虫框架 — 架构分析报告

> 只读分析，未修改任何代码。阅读范围：framework/ 16 个核心模块 + gui/ app.py、pages 全部、reader 三视图、components、sources/ 样例、docs/ 三份设计文档。

---

## 1. 架构总览

### 1.1 三层职责与依赖方向

```
┌─────────────────────────────────────────────────────────────┐
│ GUI 层（gui/）                                               │
│   app.py 装配 + 8 个 Tab 页 + reader 三视图 + components      │
│   QThreadPool/QRunnable 包后台任务，Signal 回主线程           │
└───────────────┬─────────────────────────────────────────────┘
                │ 直接 import framework.*（模式 A 直连，非文档承诺的 EventBus 模式 B）
▼
┌─────────────────────────────────────────────────────────────┐
│ framework 层（framework/）                                   │
│   业务爬取: discovery / search / content / download_queue     │
│            / downloader / bulk_fetch / adblock               │
│   基础设施: http / parser / selfcheck / decrypter / signers   │
│            / proxy_pool / ytdlp / playwright_helper          │
│   配置与状态: config / source_manager / settings_manager      │
│            / events / cookie_manager / preview               │
│   播放: vlc_player（重度依赖 Qt，破坏"框架纯 Python"承诺）     │
└───────────────┬─────────────────────────────────────────────┘
                │ 只读 raw dict（无类型化 schema 模型）
▼
┌─────────────────────────────────────────────────────────────┐
│ 源配置层（sources/*.json）  = 全部站点知识                      │
└─────────────────────────────────────────────────────────────┘
```

依赖方向总体单向、无 import 环（framework 不 import gui）。但**文档承诺的 Scheduler 调度中枢与 render 模块在代码中不存在**，调度职责被 gui/app.py 的装配代码和每个类自己承担——这是文档与实现最大的偏差。

### 1.2 数据流

```
用户操作
  ├─ 发现页:   Discovery.list_categories/list_works
  ├─ 搜索页:   Search.search_one/search_type（并发 worker，每源独立 HttpClient）
  ├─ 阅读:     ReaderPage → Content.fetch_detail/fetch_chapter/fetch_comic_pages/
  │            fetch_video_streams（后台 QRunnable + Signal）
  ├─ 下载:     DownloadQueue（并发槽）→ Downloader → Content.fetch_* →
  │            ffmpeg_merger(视频) / epub_builder(小说/漫画)
  └─ 全量抓取: BulkFetch → Discovery.list_* → JSON 索引

每条链路内: HttpClient(抓取) → Parser(解析 source.raw 规则) → Decrypter(可选解密)
            → 统一 dataclass(Detail/Work/SearchResult/Chapter) → GUI 展示/下载
```

文档宣称的 EventBus 模式 B 与实现不符——EventBus 实际只用于下载进度、主题、全量抓取进度三类事件；搜索/详情/分类全部走"QRunnable + 同步调用 + Signal"的直接绑定，且 framework 通过 `on_page`/`image_progress_cb`/`health_reporter` 回调反向侵入 GUI 的执行节奏。

## 2. 优点（值得保留）

1. **配置驱动的核心思路贯彻得好**：新增站点 = 新增 JSON。bilibili（API 直调 + wbi 签名）、youtube（yt-dlp）、18mh（AES 加密图）、comicbox（Playwright canvas 分片）四类完全不同的站点都通过配置差异化表达，未污染框架代码。

2. **异常体系干净**：`errors.py` 的 `SourceError` 基类统一携带 `source_id`，全链路 `to_user_text()` 输出用户可读错误，配合失效源隔离，鲁棒性目标基本落地。

3. **代理池/反爬换 IP 是高质量工程**：`ProxyPool` 用 `RLock` 实现线程安全、auto 池"触发反爬才启用"语义、`HttpClient._run_with_proxy_switch` 换 IP 外壳，设计清晰、注释详实。

4. **对坑的理解深入且沉淀在代码注释里**：requests Session 非线程安全（多处主动规避）、Windows 管道缓冲死锁（ytdlp 用临时文件重定向）、VLC gnutls TLS 不兼容（本地代理降级）、m3u8 广告段过滤、VLC HWND 变化重挂。

5. **章节排序逻辑**（`_extract_chapter_number`）：阿拉伯/汉字/大写/罗马/全角/英文 Vol.Ch 全兼容的卷章复合排序，是高质量独立纯函数，值得保留并建议抽离。

6. **QRunnable + epoch 防竞态模式**：discover_page 用 `_source_epoch` 让旧请求回调整体失效，是 GUI 异步的正确姿势。

## 3. 问题与风险

### 3.1 耦合过重

**[P1] GUI 直接依赖 framework 内部实现 + 直接读配置 raw dict**
- 位置：`gui/app.py:969`、`gui/pages/source_page.py:95,182,525`、`gui/pages/search_page.py:392`、`gui/pages/reader/video_view.py:355`、`gui/components/source_editor.py:228,904`
- 问题：GUI 层直接 `source.raw.get("api_endpoints")...` 解析源配置，绕过 SourceConfig 封装。source_page 甚至复刻了 `StructureChecker._selfcheck_url` 的 URL 判定逻辑（三处重复）。
- 影响：改字段名/结构调整要同步改 GUI 且不会编译期报错。
- 建议：SourceConfig 提供只读访问器（`quality_options()`、`needs_image_decrypt()` 等），GUI 禁止触碰 raw。

**[P2] framework 依赖 Qt，破坏"框架纯 Python"承诺**
- 位置：`framework/vlc_player.py:22`（无条件 `from PySide6.QtCore import ...`）、`framework/download_queue.py:25-28`（可选导入）
- 建议：VLC 播放器整个属于 GUI 资产，应移到 gui/；若必须留 framework，用延迟导入。

**[P3] framework 通过可变回调字段反向绑定 GUI**
- 位置：`content.py:1041-1049`（on_page）、`downloader.py:126,138`（image_progress_cb）、`download_queue.py:458-460`、`content.py:310`/`discovery.py:70`（health_reporter）
- 建议：统一收敛到 events.py 事件总线，framework 只 emit，不直接调用。

**[P4] 框架 dataclass 被 GUI 污染**
- 位置：`discovery.py:315-317`（Work._needs_cover_decrypt 动态挂私有属性）、`novel_view.py:203,260,382`（Chapter._cached_text/_cached_pages 由 GUI 写）
- 影响：dataclasses.replace/深拷贝/复用会丢缓存或产生隐藏依赖。

**[P5] `_DownloadWorker` 同名重复定义（死代码 + 隐患）**
- 位置：`download_queue.py:42-64` 普通版 + `:750-777` QRunnable 版，后者**遮蔽**前者。
- 影响：两个类行为语义必须人肉对齐，隐藏双实现漂移。

### 3.2 单一职责被破坏

**[P1] content.py（1817 行）是"全家桶"**
- 一个类同时承担：详情页解析、章节列表、章节序号数字解析（约 200 行纯排序逻辑）、章内分页探测、漫画图集、图片 AES 解密+data URI、视频双流、yt-dlp 引擎、换源、广告过滤、Playwright 渲染调度。
- 影响：任何链路改动都碰这一个大类；`_get`/`_headers`/`_timeout` 样板在 content/discovery/search 三处重复。

**[P2] 下载器语义混杂**：`downloader.py` 的 `_download_comic` 同时做"抓图+并发下载+累积到 epub"，与 settings 设计的"逐章落盘 .txt/.jpg/.mp4"目标相悖。

**[P3] app.py（1088 行）是超级装配器**：跨页协调全堆在 MainWindow，`_bg_image_qss_block` 等纯渲染细节不该在装配器里。

### 3.3 扩展性瓶颈

1. **新增内容类型**（第 4 种）要动：config.py CONTENT_TYPES、content.py 8+ 处 `if content_type ==` 分支、downloader、download_queue、reader_page + 新增视图。无策略表/注册表抽象。
2. **新增解密算法**要改 decrypter.py 两处 if 链。signers.py 用了注册表是正例，decrypter 却没用。
3. **新增传输方式**：http.py 是过程式 5 个方法，无接口抽象。
4. **文档宣称的 render 引擎枚举**（playwright/pyppeteer/requests-html）实现只有 playwright + 原生 HTML。

### 3.4 线程模型隐患

**[P1] requests.Session 共享的"信念分裂"**
- `search.py:111-127`、`discovery.py:349-375` 显式建独立 HttpClient；而 `downloader.py:127-138` 在 8 线程里**共享** `self._http.get_bytes`；`content.py:1150-1172` 又改用 urllib。
- 建议：统一规则——**每个后台任务/worker 持有独立 HttpClient**，封装成工厂方法 `HttpClient.fork()`。

**[P2] 每请求一个 daemon Thread 做自检，无池化**
- 位置：`content.py:330-349`、`discovery.py:90-109`
- 建议：自检改为单线程队列/节流，或并入线程池。

**[P3] 共享状态无锁写入**
- `source_manager.py` update_health 无锁 + `_save_health` 直接 write_text，并发写可能截断 JSON。
- `ytdlp.py:44` `_search_cache` 类级 dict 无锁；`content.py:307` `_ytdlp_stream_cache` 无锁。
- `config.py:155-169` `_proxy_pool` 惰性构建无锁。

**[P4] EventBus emit 无线程亲和性约束**
- `events.py:68-77` 在 QThreadPool worker 线程里 emit，bus 同步调用订阅者，若订阅者直接操作 Qt 控件会在非 GUI 线程碰 Qt。
- 建议：EventBus 增加"emit 必须进 Qt 主线程"的桥接。

**[P5] QRunnable 防 GC 手动持引用模式遍布全 GUI**
- 位置：reader_page、video_view、novel_view、discover_page 各 `self._xxx_task`。
- 建议：封装 TaskRunner 组件（持有任务引用 + 完成后自动释放 + epoch 失效）。

### 3.5 配置驱动 schema 的一致性

1. **校验浅**：from_dict 只校验顶层 $id/$type/$name 和 base_url；endpoints/search/detail/content/decryption 全不校验。
2. **`$schema_version: 2` 从未被读取**：无版本检查/迁移钩子。
3. **raw dict 访问分散重复**：`source.raw.get("endpoints",{}).get("content")` 在 content.py 重复 7+ 次。
4. **JSONPath 解析 6 份近似实现**：discovery/_simple_getpath、content/_jsonpath、search/_simple_getpath 等，行为细节有差异。
5. **URL 拼接/解码辅助重复**：_abs_url、_diag_url、mime 猜测各两份以上。

### 3.6 全局可变状态

| 位置 | 状态 | 风险 |
|---|---|---|
| vlc_player.py:24,28 | 模块级 _INSTANCE + _PROXY_SESSION | release 顺序依赖 aboutToQuit 钩子 |
| proxy_pool.py:252 | _GLOBAL_PROXY_CFG 全局缓存 | 热更新依赖手动 reset |
| adblock.py:166 | _default_engine 模块级单例 | 多配置场景无法区分 |
| ytdlp.py:44 | _search_cache 类级 dict | 跨实例共享 + 无锁 |
| playwright_helper.py:44-46 | _SYNC_BROWSER 单例 | 无显式关闭路径 |

### 3.7 资源生命周期

- **VLC 生命周期**：模块单例 Instance + 每播放器 MediaPlayer + 每播放器 VlcStreamProxy（ThreadingHTTPServer）。释放顺序强依赖约定（必须先 player.close() 再 shutdown_vlc），新播放器创建点忘记 close 就泄漏本地 HTTP 服务线程。
- **requests.Session 无关闭路径**：app.py 创建 self.http 后从不在退出时 close()。
- **QThreadPool 全局单例混用**：下载/封面/详情任务全塞进 globalInstance()，download_queue 并发槽只约束下载，封面/详情不受限。

### 3.8 可测试性

- `tests/` 目录**只有一个 test_proxy_pool.py**。
- 测试策略实际是 15+ 个 `_smoke*.py` 脚本，无断言、无 CI。
- 模块构造依赖手工装配，无 factory/容器。
- framework 直接依赖 requests/lxml/playwright/vlc/yt-dlp，无接口抽象。

## 4. 重构建议（高价值低风险，不改行为）

### 建议 1：抽 `HttpClient.fork()` 工厂 + 统一线程边界规则
- 改动范围：http.py 加 fork()；收敛 search.py/discovery.py 的复制；downloader 8 线程共享改每线程 fork。
- 收益：消除三种处理方式分裂，统一并发模型，解除下载并发风险。风险低。

### 建议 2：把 content.py 的章节序号解析抽成独立模块
- 改动范围：_cn_to_int/_roman_to_int/_extract_chapter_number/_sort_chapters（content.py:37-264 约 220 行）→ framework/chapter_sort.py。
- 收益：content 瘦身，该逻辑可独立单测。风险低。

### 建议 3：统一 URL 拼接 / JSONPath / mime 三类辅助函数
- 改动范围：新建 framework/utils.py，收敛三处 _abs_url、六份 _jsonpath、两份 mime 猜测。
- 收益：删除约 150 行重复。风险低。

### 建议 4：GUI 层禁止触碰 source.raw，给 SourceConfig 补访问器
- 改动范围：SourceConfig 增加 quality_options()/needs_image_decrypt() 等；替换 GUI 直接 raw 访问。
- 收益：GUI 与源 schema 解耦。风险低。

### 建议 5：封装 TaskRunner 替换散落的 QRunnable 防 GC 持有
- 改动范围：新建 gui/components/task_runner.py；替换 discover_page/reader_page/novel_view/video_view 的散落持有。
- 收益：彻底消除"引用防 GC"类 bug。风险中低。

## 5. 架构演进建议

1. **先还"分层账"：把 Scheduler 补回来或正式废弃**。要么抽出 framework/scheduler.py 提供 CLI 与 GUI 共用编排入口，要么更新文档承认"装配即调度"。
2. **把配置层升级为类型化模型 + 完整校验**。用 dataclass/pydantic 描述 endpoints 结构，from_dict 全量校验，访问器取代散落的 raw.get。
3. **内容类型策略化**：用注册表替换 content.py 里 8 处 if/elif，解密/签名/渲染引擎同样注册表化。这是"插件化"的第一步。
4. **进程边界治理（分布式前奏）**：framework 暴露纯 Python API + 明确持久化层，把"爬取内核"与"展示端"解耦成可独立部署的进程。GUI 的 VLC/Qt 资产全部下沉到 gui 层。
5. **并发与资源模型统一定义**：每任务独立 HttpClient + fork()、全局线程池配额、后台自检并入池、EventBus emit 强制 Qt 主线程桥接。
6. **测试资产补建**：把 _smoke*.py 中最有价值的链路转成 pytest 用例，优先为 chapter_sort、parser、proxy_pool、settings_manager 建断言体系。

---

**一句话总结**：这是一个"内核能力很强、分层纪律松散"的框架。代理池、解密、解析、播放降级等单点工程质量优秀，但内容类型硬编码在 content.py 里、GUI 直连 framework 且直接读 raw dict、文档承诺的 Scheduler/EventBus/测试体系均未落地。当前规模下可运行，继续叠加源类型与站点只会加速三类债的堆积：raw schema 的重复解析、GUI 对 schema 的隐性依赖、以及 QRunnable/线程持有模式的散落复制。
